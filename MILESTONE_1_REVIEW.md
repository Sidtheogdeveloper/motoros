# MotorOS — Milestone 1 Engineering Review

**Review date:** 24 October 2026, Asia/Calcutta.  
**Scope:** Actual source, clean builds, running APIs, PostgreSQL, Compose, containers, frontend/BFF, security boundaries and automated tests. No Milestone 2 features or cloud resources were implemented.

## Gate decision

**PASS for the local Milestone 1 foundation after the fixes below.** No unresolved critical Milestone 1 failure was found in the exercised paths. The code can be the starting point for Milestone 2. This is **not** production approval or confirmation that the complete MotorOS product is implemented.

The initial 14-test suite passed before review, but did not detect several important input and authentication-contract defects. This review reproduced those defects over real HTTP, fixed them, and expanded regression coverage. Passing the original tests alone was insufficient.

Production remains blocked on identity/RBAC hardening, RLS strategy, comprehensive security scanning and later operational controls. Those gaps are distinguished from the working local foundation below. Milestone 2 has not been started.

## Issues found and fixed

Severity describes the consequence in the delivered foundation; production concerns are listed separately. These fixes are in the source, not merely proposed.

| Finding                                                   | Before review                                                                                                                                                                                                                                       | Fix and regression evidence                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **High: incomplete JWT identity contract**                | Correctly signed tokens without `exp` or `sub` were accepted by all three services. Missing branch claims could be accepted or fail inconsistently. The original signer normally supplied these fields, so this was not a signature-forgery bypass. | Added `LocalClaimsValidator` to every service's decoder. It requires canonical UUID subject/tenant, a recognized role, a UUID branch list, issued/expiry times, bounded 15-minute lifetime and sane issuance time. Missing/malformed identity tokens now return 401. Added validator unit tests and actual HTTP tests against all services. Existing issuer/audience/signature checks remain. |
| **High: omitted optimistic-lock version allowed an edit** | The primitive `long` request field defaulted to zero when omitted; a new work order could therefore advance without the caller supplying its version.                                                                                               | Changed the request to `@NotNull @Min(0) Long`. Missing version now returns 400 without changing the record or adding an audit row. Two real concurrent PATCH requests additionally proved exactly one 200, one 409 and no losing audit entry.                                                                                                                                                |
| **Medium: client errors reported as server failures**     | Missing required branch parameter, unsupported method and unknown route returned 500 through the catch-all advice.                                                                                                                                  | Preserve Spring `ErrorResponse` status and headers while keeping the body sanitized. Verified 400, 405 with Allow header, and 404 in integration/HTTP tests.                                                                                                                                                                                                                                  |
| **Medium: UTF-8 password boundary**                       | Character validation allowed a password longer than BCrypt's 72-byte input limit; registration then returned 500.                                                                                                                                   | Check UTF-8 byte length before hashing or writes; frontend validation agrees. Oversized input returns 400 and an integration test verifies no workshop was persisted.                                                                                                                                                                                                                         |
| **Medium: BFF body limit buffered before enforcing**      | The BFF read the full body, then checked JavaScript character count. Chunked/multibyte requests did not have a bounded-byte read.                                                                                                                   | Added a bounded stream reader that counts bytes, cancels oversized input and rejects invalid UTF-8. Verified with Node tests and a real chunked HTTP request without Content-Length.                                                                                                                                                                                                          |
| **Medium: invalid cookie prevented reauthentication**     | An existing invalid/expired session token was forwarded even to public local login/register endpoints, where the backend bearer filter could reject it before credential login.                                                                     | Public auth calls do not forward the old bearer token; 401 responses on protected BFF calls clear the rejected cookie. | **Medium: weak process ownership/readiness**              | Startup could announce success before frontend readiness, did not supervise child exit, and could mistake an existing listener for a service it had launched. The full root startup command also passed.                                                                                                                              |
| **Low: container port mismatch**                          | Dockerfile advertised 8080 while applications defaulted to service-specific ports.                                                                                                                                                                  | Set container `PORT=8080`; all three images built, ran as user `motoros`, served health on advertised ports and passed live API/container-network checks.                                                                                                                                                                                                                                     |

## Security and incomplete functionality

The following remain **production blockers or later-milestone work**, rather than verified functionality:

1. **Identity and authorization:** local BCrypt login, shared HMAC secret and short-lived claims are suitable only for the isolated development foundation. Cognito/OIDC/JWKS, MFA/account recovery, invitations, real per-branch membership administration, regional access and immediate token revocation are absent. Complete least-privilege roles and assigned-job mechanic scope are not implemented. Customer-role access to staff endpoints is denied; a customer self-service portal is not implemented.
2. **Tenant defense in depth:** application predicates and composite ownership constraints are verified. PostgreSQL tenant RLS is **not implemented**. Schema roles isolate services, not individual tenants within a service; a future missing tenant predicate remains a risk requiring RLS/transaction-context design and further adversarial testing.
3. **Local exposure and secrets:** native APIs and database ports bind to loopback; credentials are generated locally. Local Compose deliberately passes database secrets through environment variables; Docker administrators can inspect them. `.env` file permissions on Windows do not establish a hardened ACL policy. Production needs managed secrets and TLS. Production-server browser tests explicitly used `COOKIE_SECURE=false` for loopback HTTP; that setting must not be used for a public deployment. The CSP still permits inline scripts/styles and is not a finished nonce-based production policy.
4. **Abuse controls:** authentication throttling is an in-memory IP bucket; the local BFF makes users share the backend's observed address. It is not durable or distributed and can affect other local users. Domain API quotas and comprehensive request/connection limits are unfinished. Login failure timing is not an account-enumeration-resistant production design.
5. **Audit and data lifecycle:** work-order changes and sensitive history reads are audited. General customer/vehicle access and change audits, retention/export/erasure, backup/restore exercises and disaster recovery are absent.
6. **Business scope:** work-order approval/estimate status names are lifecycle positions only. They do not prove customer consent, inspection completion, repair approval, financial correctness or physical parts handling. Appointments, inspections, inventory, billing, payments, notification delivery, event outbox/consumers, subscriptions and all five AI features remain unimplemented. No AWS resources were provisioned.
7. **Reliability and contracts:** POST creation is not retry-idempotent. History retrieval is not paginated. The UI loads the first 100 list records, and displayed operational counts use that loaded subset. DTOs are handwritten and returned entities couple public contracts to persistence. Full load/failure/soak tests, database restoration, browser coverage beyond Chromium and a formal accessibility audit were not performed.
8. **Security scan scope:** npm audit was run; a comprehensive Java advisory scan, container OS/image vulnerability scan, SAST/DAST and independent penetration test were **not** completed. Image tags are versioned but not pinned to immutable digests. Do not infer a clean security bill from functional test results.

## Maintainability and Milestone 2 readiness

The service boundaries are real: no cross-service schema queries were found. Work Order verifies vehicle access through the Customer API with bounded timeouts, then writes only its own tables. Composite customer/vehicle ownership keys and optimistic locking are meaningful database controls. There is no unnecessary scaffold of nonfunctional future microservices.

Before adding substantial Milestone 2 code, create a version-control checkpoint of this reviewed source (without `.env` or `.runtime`). The initialized repository currently has no commit history, making normal change review and rollback unavailable. No commit author was invented and no repository was pushed during this task.

Recommended near-term engineering work is to split the large `workspace.tsx`, move growing orchestration into application/domain services, separate API response DTOs from entities, add contract-generation/drift checks and make the state-transition table independent of enum ordering. The current ordinal-based state machine passed its tests, but is fragile when inserting new statuses. Keep public deployment blocked while implementing the planned identity and tenant-isolation controls.

**Milestone 2 gate:** local foundation may proceed after reviewing this report and recording the source checkpoint. No critical tested Milestone 1 failure remains open. No Milestone 2 implementation was performed as part of the review. Production/pilot commercial readiness is not granted.
