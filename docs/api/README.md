# MotorOS API contracts

Generated snapshots live in `packages/api-contracts/openapi/`. Run `npm run export:openapi` with local OIDC fixtures and the app running to regenerate authenticated service documents. Service `/v3/api-docs` and Swagger endpoints require bearer authentication; `/actuator/health` is public. JWTs must have the intended API scope. Domain calls require an authorized selected brand; tenant path parameters must match it.

Browser domain APIs use `/api/backend/{tenant|customer|workorder}/...`. The BFF supplies bearer tokens and authoritative session selection; scoped browser requests include `X-MotorOS-Expected-Tenant` as a stale-tab guard. It is not an authorization credential. Cookie-authenticated mutations require exact Origin. Direct APIs use `X-MotorOS-Tenant` only as a selection request; live membership and resource checks authorize it. The custom `/auth/register` and `/auth/login` password APIs were removed; registration/recovery happen at the IdP.

Pagination is zero-based page and size (1–100), stable ordering. Staff supports q/role/branchId; invitations return metadata/status/delivery only, never secret/hash; branch/staff/invitation UI pages use 20 records. Customer/vehicle/work-order screens retain the M1 first-100 operational list limitation. Work-order lists use branchId or privileged `allBranches=true`. History permits completed same-brand records but operational access stays assigned-branch scoped.

Mutations use optimistic `version` where applicable. Status moves supply `{status,version,note}`. Errors carry status/title/correlationId: 400 input, 401 authentication, 403 permission, 404 inaccessible record, 409 conflict/used or expired invitation/context change, 503 dependency unavailable. The BFF may return title-only transport errors. Requests and audit logs exclude credentials and customer contact bodies. Creation is not retry-idempotent; do not automatically retry POST. Invitation email has a transactional outbox; general domain events/outboxes remain future work.

## Milestone 3 registry APIs

All routes below are owned by Customer Service, require a verified user and live tenant context, and are reached through `/api/backend/customer/...` by the browser. The service OpenAPI now declares bearer authentication and the selected-tenant header. The BFF supplies that header from its session; caller selection alone grants no access. Shared registry response types are in `packages/api-contracts/index.ts`.

| Route                                                    | Contract                                                                                                                                                        |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET/POST /api/customers                                  | q searches name, primary and additional contacts; status/page/size filter and paginate; create name/email/phone/address/city/country                            |
| GET/PATCH /api/customers/{id}                            | Contact-authorized profile; PATCH supplies complete editable fields and current version                                                                         |
| GET /api/customers/duplicates                            | email/phone/country lookup; tenant-local candidate records, no automatic merge                                                                                  |
| GET/POST /api/customers/{id}/contacts                    | Additional EMAIL/PHONE contacts with label/value and optional separate-person review reason                                                                     |
| POST /api/customers/{id}/contacts/{contactId}/deactivate | Versioned soft deactivation                                                                                                                                     |
| GET/POST /api/vehicles                                   | q searches normalized registration, VIN and make/model; status/customerId/page/size; registration includes owner and optional VIN/year/fuel/color/acting branch |
| GET/PATCH /api/vehicles/{id}                             | Technical profile; customerId omitted without CUSTOMER_READ; versioned edit cannot transfer ownership                                                           |
| GET/POST /api/vehicles/{id}/ownership                    | Paginated historical relationships; transfer requires customerId/version/reason/assigned branch, plus ownership-write and contact-read permissions              |
| GET/POST /api/vehicles/{id}/odometer                     | Paginated append-only kilometers log; supplied reading/active assigned branch required; decreasing readings return 409                                          |
| GET /api/vehicles/{id}/timeline                          | branchId/page/size; authenticated delegation to Work Order Service, completed same-brand records and stable source references                                   |
| GET /api/{customers or vehicles}/{id}/documents          | Paginated AVAILABLE metadata; technical/private visibility filtered by permission                                                                               |
| POST /api/{customers or vehicles}/{id}/documents/uploads | Safe fileName, contentType, byteSize (1 byte–10 MB), sha256, branchId, visibility; returns documentId and five-minute signed PUT URL/headers                    |
| POST /api/documents/{id}/complete                        | Current pending version, fresh authorization, expiry and actual byte validation; publishes immutable separate object                                            |
| POST /api/documents/{id}/download                        | Fresh permission check; 60-second attachment GET grant; never a permanent public URL                                                                            |
| POST /api/documents/{id}/archive                         | Current version and authorized assigned branch; stops new grants, preserves retention metadata/object                                                           |
| GET /api/{customers or vehicles}/{id}/audit              | Customer-sensitive permission required; paginated actor/tenant/branch/event/time/correlation/outcome                                                            |

Work Order Service owns `GET /api/vehicles/{id}/timeline` as the authoritative service-record API. It independently checks the user, tenant, active acting branch and VEHICLE_HISTORY_READ, verifies the vehicle through Customer's API and audits access. Both service identities and original signed user tokens are required for delegation. The timeline contains id/vehicleId/branchId/createdAt/updatedAt/status/summary/source (service, resourceId, path), totalElements and totalPages; only delivered/closed records are included. An unavailable dependency returns 503 instead of fabricated history. Inactive vehicles retain readable history but cannot create new work orders.

Duplicate email/phone writes return 409 unless a separate-person review reason is supplied. An edit that leaves normalized contacts unchanged retains prior review and does not require a fresh reason. Vehicle registration/VIN duplicates always return 409; repair an existing record rather than merging or forcing a new identity. Updates and transfers reject stale versions with 409. Odometer corrections/backdating and ownership backdating are not provided. Registration branch omission is retained for M1 API compatibility; the new UI requires an acting branch.

Document URLs are short-lived bearer capabilities. Lists omit object keys/hashes. Pending upload expiry is separate from published document retention. Client downloads use credential-omitting CORS fetches and attachment blobs, so application cookies are not forwarded to local object storage. PDF/PNG/JPEG magic checks do not mean malware scanning or deep file validation.
